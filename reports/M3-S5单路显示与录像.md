# M3 / S5 单路接收、显示与录像

2026-11-28，Windows 本机回环。对应 Issue #6 的 7232901151。测试使用电脑合成视频，实板同场对照待操作者确认。

## 数据路径

FFmpeg 通过一条 RTSP/TCP 连接接收 H.264。一路将压缩视频直接封装为 `recording.ts`，另一路将同一压缩视频封装为 MPEG-TS 后写入本机管道。ffplay 只读管道，只在显示时解码。接收结束后，再单独解码已保存的文件验证回放。服务端日志按每轮 `is reading from path` 的条数核对客户端数量。电脑在这条连接上被动记录 RTP 帧结束包完整到达时的系统时刻，同一批 TCP 读取中的包可以有相同的到达时刻。

视频为 640×360、60 fps，编码器输入前写入可从画面还原的帧号并记录本机时钟。ffplay 使用 `nobuffer`、`low_delay`，软件渲染到 SDL 测试输出。根据 SDL 写出每张完整图片的时间计算帧龄，剔除首帧后 2 秒预热。将显示出的每个帧号与录像中实际解码出的帧号逐个核对。显示缺口的分母取显示窗口首尾之间的录像帧数。录像缺口另按整个文件首尾之间的编号计算。

## 结果

| 运行时长 / 主动丢帧 | 显示帧 / 同窗口录像帧 | 帧龄中位数 / p95（ms） | 接收最大间隔（ms） | 全片解码帧数 |
|---|---:|---:|---:|---:|
| 16 秒 / 开 | 829 / 833 | 61.41 / 75.66 | 31.707 | 963 |
| 16 秒 / 关 | 825 / 825 | 87.59 / 233.09 | 31.955 | 955 |
| 310 秒 / 关 | 18,456 / 18,456 | 71.78 / 111.73 | 32.349 | 18,587 |
| 310 秒 / 开 | 17,945 / 18,466 | 63.59 / 77.84 | 33.161 | 18,596 |

关闭主动丢帧的长测取得 309.948 秒连续接收，计分的显示窗口为 307.574 秒，显示端最长相邻输出间隔为 186.88 ms。录像时长 309.783333 秒，文件内的帧号连续。接入到首个可解码帧、关闭管道收尾以及计分预热的边界各不相同，原始数据分别保留了接收、录像和显示的数量。

打开主动丢帧的长测连续接收 309.976 秒，录像时长 309.933333 秒。显示窗口中跳过 521 个编号，占 2.82%，录像中这些帧均可解出。相对关闭模式，本次中位帧龄少 8.19 ms，p95 少 33.89 ms。四轮服务端各有一个读取会话，接收的 RTP 序列均连续，四个文件均通过 FFmpeg `-xerror` 全片解码，且文件内没有缺号。本机结果支持在候选入口中优先关闭主动丢帧。对之前直连 RTSP 产生的 0.52% 缺口，旧试验还涉及不同的管道与默认策略，无法单独归因。

现场使用板载 AP、真实镜头和显示器。实验中的 SDL 输出不含显示器扫描、相机曝光或无线传输耗时。此前实板测出的光学延迟 603 ms 仍是当前现场基准。

## 重跑

以下命令在仓库根目录执行。需要 Python、FFmpeg 9.0.2、ffplay 9.1 和 MediaMTX 1.21.4。每次使用新的输出目录。`summary.json` 为阶段汇总，`arrival.json` 记录主机纳秒时刻、RTP 时间戳和序列号，`display.json` 记录源帧号及发送、显示时刻，`recorded-ids.json` 列出逐帧从录像读出的编号。

[四轮原始记录和指标](data/M3/bench/2026-11-28-single-reader.json.gz) 仅包含本机合成数据。按阶段取 `display` 的第三列减第二列并除以一百万，求中位数及第 95 百分位即得表中的帧龄。取 `arrival` 的第一列相邻差并求最大值得接收最大间隔。现场尚未获得这套接收器的指标。

```text
python -m tools.analysis.m3_single_reader <短测目录> <ffmpeg.exe> <mediamtx.exe> <ffplay.exe> --seconds 16 --modes drop keep
python -m tools.analysis.m3_single_reader <长测目录> <ffmpeg.exe> <mediamtx.exe> <ffplay.exe> --seconds 310 --modes keep drop
```

现场入口和回放路径见[调试台说明](../station/bench/README.md)。对照向导分别为 VLC 200 ms 和低延迟候选启动一轮；每轮需要独立的「拍」确认。视频连续性的主判据为帧结束包到达时间线，辅以录像时长、参考帧号缺口和完整解码。板端清理及网络恢复分别记录。新入口默认关闭 ffplay 主动丢帧，原调试台默认播放器保持 VLC。

通过 `--compare-players --simulate` 完整执行了向导的两轮流程。VLC 与 ffplay 分别收到 62.077、62.448 秒连续视频，各使用一路服务端读取会话，录像可完整解码出 3,719、3,740 帧。[入口验证数据](data/M3/bench/2026-11-28-receiver-entry.json)

## Claude 复核后的连接方式与回放

通过实际对照向导用本机合成源跑了四轮。直连时，VLC 和 ffplay 的 MP4 分别完整解码出 3,722、3,742 帧；中继时分别为 3,713、3,714 帧。四轮每轮都只有一个源端读取会话，参考帧号缺口均为零。两个中继轮的连续接收时长分别为 62.094、61.976 秒。[路径对照与转换校验数据](data/M3/bench/2026-11-28-receiver-route-remux.json)

以上 310 秒测试均经过 RTP 诊断中继。复核后的现场候选默认直连视频源。向导在两轮开始前读取同一个 `--rtp-diagnostic` 开关，显式开启时 VLC 与 ffplay 都使用中继。直连轮检查录像时长、帧号和完整解码；接收端 RTP 的逐帧到达时间只在中继轮测量。

低延迟接收结束后用 FFmpeg `-c copy -movflags +faststart` 把 TS 中的 H.264 复制到 MP4。完成后才发布 `recording.mp4`；失败时保留 `recording.ts` 和 `remux.log`。另取两次 310 秒长测的 TS 副本进行转换，用 `ffmpeg -nostdin -v error -xerror -i <文件> -map 0:v:0 -f framehash -hash sha256 -` 对 TS、MP4 分别解码，按顺序比较每帧像素摘要。两组分别为 18,587、18,596 帧，全部一致，两个 TS 的文件哈希在转换前后相同。
