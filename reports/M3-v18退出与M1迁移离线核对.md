# v1.8 播放器退出与 M1 迁移离线核对

现场基线 `601f108`，幻尔 v1.8-0-gc2d1f5c。以下以 11 月 28 日 AP 实拍、v1.8 标签源码、只读旧卡镜像为依据。尚未进行新一轮拍摄、重部署或长跑。[现场时间线与证据](M3-单卡固件切换记录.md)

## 播放器退出

VLC 日志记录了主动发出 `TEARDOWN`，播放器正常退出。板端最后一条编码记录为 00:20:03.975；播放器进程在 00:20:04.467 退出，相差 0.492 秒，编码记录在前。最后一条主线程心跳更早，为 00:20:02.618。串口输出由电脑单独的读取线程加接收时间戳；日志没有记下板端最后执行的位置，也没有收到 `TEARDOWN` 的板端时间戳。仅据此无法判断是编码、解释器、串口输出还是媒体服务停滞。

| 查过的路径 | 源码行为以及对现场判断的影响 |
|---|---|
| 客户端关闭轨道 | live555 的 `handleCmd_TEARDOWN` 调用 `deleteStream`。子会话停止该客户端播放，引用归零可释放 `StreamState`。H.264 客户端读的是 `StreamReplicator` 创建的副本，构建时设置最后一个副本删除后仍保留复制器。该路径不直接调用板端 Python 的 `server.stop()`。[TEARDOWN](https://github.com/canmv-k230/mpp/blob/d0d451023cedd7f4f1f2b32d507f1457e6a43c10/middleware/src/live555/liveMedia/RTSPServer.cpp#L1749) · [子会话](https://github.com/canmv-k230/mpp/blob/d0d451023cedd7f4f1f2b32d507f1457e6a43c10/middleware/src/rtsp_server/LiveServerMediaSession.cpp) |
| 编码与发送 | 原脚本等待 `GetStream()`，默认 timeout 为 −1。物理地址发送绑定同步映射缓冲区、调用 `SendVideoData`、解除映射；MPP 在会话表锁内向源队列提交数据，队列满时淘汰旧块，生产端没有等客户端取完这块数据的条件等待。没有用户态调用栈可定位实际停在哪一段。[CanMV 绑定](https://github.com/kendryte/canmv_k230/blob/v1.8/port/multi_media/RtspServer.c#L104) · [物理地址包装](https://github.com/kendryte/canmv_k230/blob/v1.8/port/multi_media/multimedia_wrap.cpp) · [队列](https://github.com/canmv-k230/mpp/blob/d0d451023cedd7f4f1f2b32d507f1457e6a43c10/middleware/src/rtsp_server/LiveFrameSource.cpp#L29) |
| 应用主动停止整个服务 | 湖北脚本先等工作线程至多 2 秒，随后停传感器、编码器和 RTSP。MPP 的 `Stop` 设置退出标志并 `join` 事件循环线程，再清理会话。实拍在设定的 125 秒服务运行时间尚未到达时就失去心跳。既有标记只在全部返回后打印，将问题直接归因为 `join` 的证据不足。[MPP 服务](https://github.com/canmv-k230/mpp/blob/d0d451023cedd7f4f1f2b32d507f1457e6a43c10/middleware/src/rtsp_server/rtsp_server.cpp#L254) |

现场判读用主线程和编码线程各自的 1 秒心跳、编码帧号、主机时钟和清理阶段记录。应区分客户端已发关闭、服务器实际收到关闭、已进入清理、清理已返回。没有相应观察点时写“未知”。后续按 Issue #6 安排，连续两次正常连接各 20 秒，中间及末尾各留 10 秒无客户端期，确认可恢复出画面并保留 USB 枚举记录；若两路串口心跳一起消失，仅能确认主机收不到心跳。

## M1 旧环境

以只读方式打开 v1.4 整盘镜像的 FAT 分区，从第 2 分区取回 `hcv` 目录。161 个文件共 14,816,273 字节。所有文件取出后都与此次源文件读取结果逐字节比较。私有配置、原图及完整提取目录留在现场电脑。

- 161 个文件中 109 个与现场基线仓库的受版本控制文件内容相符，`.py`、`.json` 比较前统一 CRLF。主入口及 `hcv/` 包共 22 个 Python 文件，17 个与对应源码相符。4 个图传探针和 `main_hcv.py` 有差异；后者仓库版增加了共享相机、CHN1 和计时分支，默认独占入口走 CHN0。
- `config.json` 与 `reports/data/M1/m1-config.json` 字段和值完全一致。用实际加载器叠加 `config.local.json` 后通过配置校验，有差异的顶层项仅 `chn_stream`、`stream`、`wifi`。迁移 M1 时可使用原检测配置。私有配置通过本地渠道保管。
- **整卡备份中的项目根目录没有正式运行入口默认读取的 `calib.json`。** 两个保留文件分别与仓库 `M2/reference.json` 和 `M2/fixture.json` 相符。仓库 `M2/field-wizard/calib.json` 来自电脑模拟演练。独占 M1 性能测试可使用原有缺标定时的名义坐标，并记录标定状态；正式毫米坐标验收仍需具有实测来源且与当前安装几何一致的标定。[配置与文件比对](data/M3/v18-migration/m1-inventory.json) · [演练来源](M2-现场向导演练.md)

在本报告的代码版本运行 `python tools/analysis/m1_migration_inventory.py <只读提取的hcv目录>` 可重算文件匹配和配置差异。脚本输出只含状态、顶层配置项名称和仓库路径。

### v1.8 长跑向导的离线验证

`station.bench.m1_v18` 使用 `tools/board/m1_v18_longrun.py` 调用同一 M1 主循环，时长仍为 610 秒。独占阶段先核实断电、版本和 GC2093 传感器模式，部署检测依赖和 M1 基线配置，等操作者输入「拍」并发出五低一高提示音。向导保存原始串口日志、回合统计、处理窗口和收尾后 `info` 的输出。当前没有 v1.8 长跑实测结果。

旧日志中的 `elapsed_us` 在资源释放后输出。新入口同时记录采集停止时的时间，并在收尾时打印最后一个未满的计时窗口。这样可同时复算采集起止总时长法、仅活动回合、活动加 GC 三种范围。非零丢帧保留原数值交负责人判断原因。

离线命令 `python -m station.bench.m1_v18 --replay reports/data/M1/pool-ref-longrun.log --runs <本机输出目录>`。回放复现了旧记录的 54,769 帧、处理 p95 最大 1,827 µs、活动回合丢帧 0、含回合间 GC 估计丢帧 107。历史记录缺少新增的采集停止时间，回放会将该项标为待复核。测试另外覆盖 6,000 µs 边界、超限、时长法少一帧及取消拍摄。向导三项联调完成后，再通知操作者。
