# M3 图传准备与分阶段探针

## 已验证的笔记本端

`station/record_rtsp.py` 以独立 VLC 实例通过 RTSP/TCP 播放并同时写入一个 MP4，网络缓存 200 ms。关闭窗口后检查输出至少可解码一帧。

```text
python station/record_rtsp.py rtsp://<K230-IP>:8554/hcv --test 1
```

本机 Windows 使用 VLC 3.0.23、MediaMTX v1.21.4 和 FFmpeg 9.0.2，用合成 320×192 H.264 流验证了同一套 VLC 播放和录制参数。无窗口 LibVLC 连到本机 RTSP 服务，5 秒记录得到 284,501 B 的 MP4，OpenCV 逐帧回放了 146 帧。原始日志和回放统计位于 `reports/data/M3/`。首轮 portable VLC 3.0.21 出现进程崩溃，之后再次启动遇到崩溃报告弹窗。最终复测直接采用 VLC 3.0.23 的 LibVLC 播放及 MP4 封装路径。现场 VLC 桌面窗口和 K230 回传延迟仍待测试。

```text
python tools/analysis/m3_vlc_smoke.py --vlc <vlc.exe> --ffmpeg <ffmpeg.exe> --mediamtx <mediamtx.exe> <new-output>
```

## 板端失败记录

首次组合探针在幻尔 K230、固件 `v1.4-19-ga7de1c8`、MicroPython `1.21.0` 上启动。原始串口输出只到传感器发现行，随后超时，raw REPL 自动恢复失败。Windows 后续仍识别 COM3。由这份日志无法确定卡在具体哪个 API。已通知用户和 Manager，等待开发板恢复后逐阶段检查。

对照了 [参考队伍代码 ed079e5](https://github.com/VincentttWang/NUEDC_2026/blob/ed079e5/2026H/firmware_G3507/k230/rtsp_camera_stream.py) 和 [其开发记录](https://github.com/VincentttWang/NUEDC_2026/blob/ed079e5/2026H/firmware_G3507/docs/k230-development.md)。对方使用 01Studio 1G、CanMV v1.8 和 STA。本实现依据幻尔 v1.4 板载 `rtsp_server.py` 及 [CanMV 原生物理地址发送接口](https://github.com/kendryte/k230_canmv/blob/main/micropython/port/multi_media/RtspServer.c)，用相机 CHN1 硬件绑定并调用 `rtspserver_sendvideodata_byphyaddr`。这轮只确认了本板固件暴露编码器及 RTSP 接口。AP 模式留到本机重连之后使用私有配置验证。

## 恢复后的阶段顺序

以下阶段均有 5 秒板端 guard，每次保持 `board.py run --stream` 连接，运行结束后验证日志中的 `HCV_RTSP_CLEANUP` 和下一次 `info`。一阶段验证通过后再启动下一阶段。

```text
python tools/board/board.py info
python tools/board/board.py put k230/hcv/stream.py /sdcard/hcv/hcv/stream.py
python tools/board/board.py put k230/hcv/stream_probe.py /sdcard/hcv/hcv/stream_probe.py
python tools/board/board.py run tools/board/m3_camera_probe.py --timeout 12 --stream
```

1. `m3_camera_probe.py` 配置 CHN0 灰度和 CHN1 YUV，从两路各取一帧，停止摄像头并释放媒体资源。
2. `m3_encoder_probe.py` 硬件绑定 CHN1，读取、计数并释放 H.264 包，确认停止编码器、解除绑定和资源回收。
3. `m3_rtsp_probe.py` 在同一硬件链路上建立并关闭 RTSP 会话。确认短探针退出后，再安排实际笔记本拉流、录像和 M1 并行性能对照。

三步板端短探针尚未复跑。M3 的 K230 回传、录像完整性、端到端延迟 ≤300 ms 和开图传后的 M1 性能未验收。

## 2026-11-21 恢复后的分段结果

用户重接 USB 后，`ports` 和 `info` 通过。先读回 `/sdcard/hcv/` 中的依赖文件，发现板上 `main_hcv.py` 与 `hcv/stream.py` 不是当前仓库版本。仅在 `/sdcard/hcv/` 上传 `main_hcv.py`、`hcv/stream.py`、`hcv/stream_probe.py`，再读回并逐个核对 SHA-256。

相机探针通过，输出 `HCV_RTSP_CAMERA,chn0=1,chn1=1` 和 `HCV_RTSP_CLEANUP,stage=camera`，退出码为 0，后续 `info` 也通过。编码探针输出到 `HCV_RTSP_STEP,configure_and_bind_chn1` 后超时。`board.py` 的安全恢复路径最终返回 raw REPL recovery failed，退出码为 3，未继续重跑、reset 或触发看门狗。RTSP 探针因此未执行。原始日志、源码 SHA 对照和本轮记录位于 `reports/data/M3/m3-20261121-2345/`。

根据 Issue #6 的复核意见，已准备 `k230/hcv/stream_bind_probe.py` 和单步入口，拆开 CHN1 配置、`SetOutBufs`、`Create`、`bind_info`、`MediaManager.link` 以及 `MediaManager.init()` 的先后关系。每个入口使用 5 秒 guard 和独立资源清理。探针顺序覆盖官方示例的 `link → MediaManager.init → Create`，以及 `Create → link → init`、`init → Create → link` 对照。

## 2026-11-22 官方示例只读核对

K230 重接后 `ports` 与 `info` 通过。只读列出 `/sdcard/examples/`、`02-Media` 和 `17-Sensor`，取回的文件和清单在 `reports/data/M3/official-examples-20261122/`。没有运行官方示例。板上 `02-Media/video_encoder.py` 与 `rtsp_server.py` 的主要生命周期是：`Sensor` 配置、`Encoder.SetOutBufs`、`MediaManager.link(sensor.bind_info()['src'], ...)`、`MediaManager.init()`、`Encoder.Create`、`Encoder.Start`、`sensor.run()`。官方示例使用默认 CHN0，不能直接证明本项目 CHN1 与 90 fps 组合可用，但可作为本固件 API 调用顺序依据。

按批准的细分顺序，CHN1 配置、`SetOutBufs`、`Create-before-init` 均能返回，并在显式 `sensor.stop()`、`Sensor.deinit()` 后保持下一次 `info` 正常。官方顺序的前半段 `bind_info(chn=1)` 也能返回，但下一步 `MediaManager.link` 卡住，主机最终退出码 3，raw REPL 无法恢复。原始日志在 `reports/data/M3/m3-20221122-bind-order/`。因此当前卡点已缩小到 CHN1 → VENC 的 `MediaManager.link` 调用，尚不能归因到某个参数或宣称 CHN1 不支持。下一轮需要再次断电重接后再决定是否测试 `Create → link → init` 和 `init → Create → link` 对照。

## 2026-11-22 CHN0 官方基线初测

完全断电重接后，主机 COM3 可以打开，被动监听 10 秒收到 0 字节，`info` 通过。CHN0 官方顺序探针完成了传感器配置、`SetOutBufs`、`MediaManager.link`、`MediaManager.init`、编码器创建与启动、`sensor.run`，并输出 `HCV_CH0_READY,url=rtsp://0.0.0.0:8554/hcv`。首轮随后因探针向官方 `rtspserver_sendvideodata` 传入 `bytearray` 而报类型错误，清理标记已输出。证据在 `reports/data/M3/m3-20221122-ch0-baseline/`。

修正 `bytes` 转换后立即重跑，第二轮在首轮异常遗留的媒体 link 上卡住，不能当作 CHN0 基线失败。已把清理改为显式 `MediaManager._del_link(link)`，提交 `2237a15`。待再次重接后重跑修正版，成功后才启动笔记本拉流和录像。

后续实测发现本板固件的 `MediaManager` 没有 `_del_link` 属性。官方示例使用 `del link`，由对象生命周期释放 link。现有探针和通用 `stream.py` 已改成兼容路径：有 `_del_link` 时调用，没有时删除 link 对象引用。之前的 `2237a15` 说明只适用于有该私有方法的实现，不能作为本板最终清理方式。`stream_bind_probe.py` 的清理也已同步修正。

当前学习结论是：CHN0 官方链路已证明能完成初始化、启动传感器和输出 RTSP URL，CHN1 的卡点仍发生在 `MediaManager.link`。官方示例的逐包 `bytes` 发送只用于基线验证，项目规格仍要求图传主路径优先采用 `rtspserver_sendvideodata_byphyaddr`，避免复制和额外 GC。

## 2026-11-22 重接后的 CHN0 基线与网络前置

用户重新插入 K230 后，`ports` 枚举 COM3，`info` 返回固件 `v1.4-19-ga7de1c8`、MicroPython `1.21.0`。先重新执行只读 API 清单，没有创建媒体对象。主机检查返回 `HCV_API_OK`，原始清单保存于 `reports/data/M3/m3-20261122-reconnect/api-inventory.log`。

随后只运行一次修正版 CHN0 探针，使用本板官方顺序 `SetOutBufs → MediaManager.link → MediaManager.init → Encoder.Create → Encoder.Start → sensor.run`。结果如下：

```text
HCV_CH0_READY,url=rtsp://0.0.0.0:8554/hcv
HCV_CH0_SUMMARY,packets=278,bytes=4520422
HCV_CH0_CLEANUP
```

退出码为 0，紧接着执行 `info` 仍成功。原始串口日志保存于 `reports/data/M3/m3-20261122-reconnect/ch0-baseline.log`。这次实测证明本板固件上的 CHN0 → 硬件 H.264 → RTSP 初始化、发送和清理路径能完整运行。

为了做实际 VLC 拉流，进行了单独的 WLAN 前置检查。主机当前连接的是 5 GHz WLAN，K230 使用本地提供的凭据尝试 STA 连接，板端返回 `run connect failed`，状态持续为 `False`，IP 为 `0.0.0.0`。该脚本只做连接和状态查询，没有启动媒体链路。测试后 `info` 仍通过，原始日志保存于 `reports/data/M3/m3-20261122-reconnect/sta.log`。

因此本轮结论为：CHN0 板端媒体生命周期 PASS；真实 VLC 画面、录像和端到端延迟暂时无法测量。电脑只有一个正在使用的 WLAN 适配器，本轮没有擅自切换到 K230 AP，以免中断现有网络和 Issue 轮询。后续需要可用的 Wi-Fi 凭据，或明确批准切换到 K230 AP 后再进行 VLC 验证。WLAN 原始日志保存于 `reports/data/M3/m3-20261122-reconnect/sta.log`。
