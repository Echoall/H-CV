# M3 图传准备与分阶段探针

## 已验证的笔记本端

`station/record_rtsp.py` 以独立 VLC 实例通过 RTSP/TCP 播放并同时写入一个 MP4，网络缓存 200 ms。关闭窗口后检查输出至少可解码一帧。

```text
python station/record_rtsp.py rtsp://<K230-IP>:8554/hcv --test 1
```

本机 Windows 使用 VLC 3.0.23、MediaMTX v1.21.4 和 FFmpeg 9.0.2，用合成 320×192 H.264 流验证了同一套 VLC 播放和录制参数。无窗口 LibVLC 连到本机 RTSP 服务，5 秒记录得到 284,501 B 的 MP4，OpenCV 逐帧回放了 146 帧。原始日志和回放统计位于 `reports/data/M3/`。首轮 portable VLC 3.0.21 出现进程崩溃，之后再次启动遇到崩溃报告弹窗。最终复测直接采用 VLC 3.0.23 的 LibVLC 播放及 MP4 封装路径。现场 VLC 桌面窗口和 K230 回传延迟仍待测试。

```text
python tools/analysis/m3_vlc_smoke.py --vlc <vlc.exe> --ffmpeg <ffmpeg.exe> --mediamtx <mediamtx.exe> <new-output>
```

## 板端失败记录

首次组合探针在幻尔 K230、固件 `v1.4-19-ga7de1c8`、MicroPython `1.21.0` 上启动。原始串口输出只到传感器发现行，随后超时，raw REPL 自动恢复失败。Windows 后续仍识别 COM3。由这份日志无法确定卡在具体哪个 API。已通知用户和 Manager，等待开发板恢复后逐阶段检查。

对照了 [参考队伍代码 ed079e5](https://github.com/VincentttWang/NUEDC_2026/blob/ed079e5/2026H/firmware_G3507/k230/rtsp_camera_stream.py) 和 [其开发记录](https://github.com/VincentttWang/NUEDC_2026/blob/ed079e5/2026H/firmware_G3507/docs/k230-development.md)。对方使用 01Studio 1G、CanMV v1.8 和 STA。本实现依据幻尔 v1.4 板载 `rtsp_server.py` 及 [CanMV 原生物理地址发送接口](https://github.com/kendryte/k230_canmv/blob/main/micropython/port/multi_media/RtspServer.c)，用相机 CHN1 硬件绑定并调用 `rtspserver_sendvideodata_byphyaddr`。这轮只确认了本板固件暴露编码器及 RTSP 接口。AP 模式留到本机重连之后使用私有配置验证。

## 恢复后的阶段顺序

以下阶段均有 5 秒板端 guard，每次保持 `board.py run --stream` 连接，运行结束后验证日志中的 `HCV_RTSP_CLEANUP` 和下一次 `info`。一阶段验证通过后再启动下一阶段。

```text
python tools/board/board.py info
python tools/board/board.py put k230/hcv/stream.py /sdcard/hcv/hcv/stream.py
python tools/board/board.py put k230/hcv/stream_probe.py /sdcard/hcv/hcv/stream_probe.py
python tools/board/board.py run tools/board/m3_camera_probe.py --timeout 12 --stream
```

1. `m3_camera_probe.py` 配置 CHN0 灰度和 CHN1 YUV，从两路各取一帧，停止摄像头并释放媒体资源。
2. `m3_encoder_probe.py` 硬件绑定 CHN1，读取、计数并释放 H.264 包，确认停止编码器、解除绑定和资源回收。
3. `m3_rtsp_probe.py` 在同一硬件链路上建立并关闭 RTSP 会话。确认短探针退出后，再安排实际笔记本拉流、录像和 M1 并行性能对照。

三步板端短探针尚未复跑。M3 的 K230 回传、录像完整性、端到端延迟 ≤300 ms 和开图传后的 M1 性能未验收。
