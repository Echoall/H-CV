# 湖北图传同时找球，第 2 项电脑预案

2026-11-26，Issue #6。基线 `bb96212`，本次代码版本可用 `git log -1 --diff-filter=A -- reports/M3-湖北图传同时找球.md` 定位。实板 AP 分支①尚待验证，本轮未操作 K230。固件文件与 SHA-256 不适用。电脑环境为 Windows、CPython 3.14.6 和 NumPy 2.5.5。

## Claude 复核后的重测

当前版本在进入检测循环前分配整轮的两个 `array("I")`，每帧只记录处理时间与取图后耗时。每 60 帧记一次板端累计时间，结束后恢复 GC 再排序输出。串口仅在开始和结束时发送实时对时标记。电脑用两端的时钟偏差取保守交集，逐窗对齐显示和检测；结束后批量收到的日志时刻不参与对齐。

| 重新回放 | 全循环帧 / 秒 / 估算丢帧 | 最大窗口处理 p50/p95/p99（µs） | 最大窗口取图后 p50/p95/p99（µs） | GC 合计（µs） |
|---|---|---|---|---:|
| 90 fps 实拍条回放 | 5851 / 65.006553 / 0 | 444 / 569 / 613 | 1823 / 2254 / 2588 | 8986 |
| 60 fps 合成球对照 | 3901 / 65.011974 / 0 | 653 / 854 / 923 | 1924 / 2382 / 2435 | 8842 |

90 fps 预算 11.111 ms，当前电脑取图后 p95 为 2.254 ms。用文末脚本复算 `reports/data/M3/hubei-m1/deferred90.log`、`reports/data/M3/hubei-m1/deferred60.log` 即可复核新版结果。

**实板第一轮只测时序。** 湖北 1080p60 下 CHN1 的视场、裁剪、ROI 与标定可能对不上，VALID 和位置误差不作本轮判据。通过后保持湖北线程结构，仅把传感器换回 M1 的 720p90，按 90 fps 再测 60 s。两轮都通过后才确认图传和找球可以同时工作。

## 首版两次各 65 秒的回放（95eb144）

| 指标 | 90 fps 时间预算 | 60 fps 合成球对照 |
|---|---:|---:|
| 整个检测循环，含定期 GC 和主动让出 | 65.007701 s | 65.013630 s |
| 完成帧数 / 总时长估算少处理帧数 | 5851 / 0 | 3901 / 0 |
| 两次 GC 合计 | 7688 µs | 9325 µs |
| 纯处理 p50 / p95 / p99，µs | 434 / 557 / 599 | 641 / 818 / 887 |
| 取到图至主动让出结束 p50 / p95 / p99，µs | 1760 / 2194 / 2316 | 2022 / 2393 / 2496 |
| 找到 / VALID 帧数 | 0 / 0 | 1920 / 1904 |
| 内存串口接收 BALL / STATUS | 5851 / 129 | 3901 / 128 |
| 视频替身线程取得调度的次数 | 2101 | 2109 |

总时长口径取 `max(0, floor(循环墙钟秒数 × 源帧率) − 完成帧数)`。起点在相机预热和检测器初始化之后，终点在关闭 UART、回收媒体之前。计入等待取图、日志、每轮让出以及循环内全部 GC。百分位按连续 60 帧窗口排序，取各窗口对应百分位的最大值。完整窗口分别覆盖 5820 和 3900 帧，尾段也计入总时长法。电脑 90 fps 的单帧预算为 11.111 ms，回放的取图后 p95 用了 2.194 ms，留约 8.917 ms 给取图等待和其余开销。此数值只描述这台电脑和这组输入。

90 fps 使用仓内 `reports/data/P1-T01/board-roi3/p1_t01_sequence_roi3` 的 30 张实拍灰度条循环回放。60 fps 对照在相同像素上加亮背景，交替叠加合成暗圆和空场，检验有检测、跟踪、丢失时仍会发包。早期试跑发现原灰度条很暗，直接叠黑圆未产生有效检测。两次均未加载现场标定，毫米数值、真实钢球的识别准确率或进球延迟均待现场。UART 替身检查每一个包的长度、同步头和 CRC。视频替身用独立线程定时等待，不编码、传网或显示。

## 现场模式和验收范围

- **电脑回放及协议路径 PASS。** 调用 `main_hcv.run` 原有检测、映射、Kalman、BALL/STATUS 代码。单独运行 M1 时继续自行管理 CHN0。并行入口只借用已启动的同一个 Sensor，从 CHN1 取灰度图；媒体的初始化、停止和释放仍由湖北服务器负责。`m3_hubei_rtsp.py` 保留原独立线程的 GetStream、按物理地址发送及 ReleaseStream。
- **让出方式已配置。** `station/bench/hubei_detection.json` 设置每个完成帧调用 `time.sleep_ms(1)`。电脑读 `reports/data/M1/m1-config.json`。现场读取已部署的 M1 配置，在内存中改为湖北原生 1920×1080@60，按实际模式检查标定指纹。视频输出仍为 640×360@60，最高可取得的不同检测帧为 60 fps。原 720p90 M1 模式的标定不能直接证明此模式的精度。
- **实板同步持续时间、M1 丢帧与处理 p95 待现场。** 向导先检查纯图传实板 AP 的通过记录、录像及现场截图。随后按既有断电、自检、用户确认「拍」与蜂鸣流程执行。一次媒体会话同时采集 CHN0 与 CHN1。按电脑时钟取最长连续变化画面之内的完整检测窗口，同时检查板端计时和串口接收跨度均达到 60 s、录像至少 60 s。`summary.json` 的 `m1_during_display` 给出此段帧数、含 GC 的耗时、源帧率、总时长法丢帧、处理 p95 是否 ≤6 ms。串口接收时刻有传输和调度误差。取得完整测量和达到性能指标分别记录。
- **硬件待验证。** 同时运行的线程调度、VENC、无线传输、画面色块及延迟由现场记录判断。板上单独 M1 的 90 fps 基线见 `reports/M1-板上跑通.md`，须保留各版本及 GC 口径。

## 复算

原始证据为 `reports/data/M3/hubei-m1/pc90.log` 和 `pc60-control.log`。在仓库根目录运行，前两条为重新采电脑样本，输出路径需尚不存在。第三条直接复算已提交数据。

```powershell
python tools/analysis/hubei_m1_replay.py pc90-new.log --fps 90
python tools/analysis/hubei_m1_replay.py pc60-new.log --fps 60 --target
python tools/analysis/hubei_m1_metrics.py reports/data/M3/hubei-m1/pc90.log reports/data/M3/hubei-m1/pc60-control.log
```
