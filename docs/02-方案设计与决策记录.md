# 02 方案设计与决策记录（ADR）

版本 v1.0（2026-11-19，Manager）。

本文先给出总体架构，再逐条记录关键决策。每条决策都包含：备选方案、正方理由、反方质疑、裁决、**推翻条件**，以及用来检验它的实验。
本方案参考了同题开源作品的经验与教训（见 `reference/同题开源作品调研.md`，文中以【调研#n】引用），但每条结论仍要用我们自己的实验来验证。

## 1. 总体架构

```
             ┌──────────────────────── K230（车上）────────────────────────────┐
GC2093 ──CSI2──► Sensor ─┬─ CHN0：检测通道（灰度，小图，高帧率）──► 主循环
(1280×720@90 或           │                                        │
 1280×960@60，EXP-01 定)  │      ① 参考标记定位 → ② 找球 → ③ 倾斜补偿
                          │      → ④ 像素→mm（标定表） → ⑤ 跟踪滤波 → ⑥ 打包
                          │                                        │
                          │                     UART1 ─────────────┴──► 控制组 MCU
                          │                    （BALL 帧，每帧一次；STATUS 帧 2Hz）
                          │                     ◄── RUN_INFO（任务号、计时、目标、摆杆角）
                          │
                          └─ CHN1：图传通道（YUV420SP，≥960×540）──► 硬件 H.264 ──► RTSP ──┐
                                                                                    WiFi（AP）
                      遥测 UDP（位置 CSV，≤30Hz + 事件）────────────────────────────────┤
             └────────────────────────────────────────────────────────────────────┘    │
                                                                                         ▼
                                                         场外笔记本「Station」：显示 + 叠加 + 分段录像 + 回放 + 曲线 + CSV
```

### 1.1 板上软件模块（`k230/hcv/`）

| 模块 | 职责 |
|---|---|
| `config.py` | 读取 `config.json`、`config.local.json` 并做校验 |
| `camera.py` | 初始化 sensor 和多通道，取帧，取帧时间戳 |
| `markers.py` | 参考标记定位（3 个） |
| `detect_blob.py` | 检测器 A：阈值 + 斑点 |
| `detect_profile.py` | 检测器 B：列剖面 − 背景基线 |
| `geometry.py` | 倾斜补偿（一维射影变换）、标定表插值 |
| `calib.py` | 标定流程，读写 `calib.json`，快速复核 |
| `tracker.py` | 常速度卡尔曼（或 α-β）跟踪、门控、外推、丢失判定 |
| `proto.py` | ICD 协议编解码（与 `protocol/python` 是同一份代码） |
| `link_uart.py` | UART 收发（非阻塞） |
| `stream.py` | RTSP 推流（硬件路径） |
| `telemetry.py` | UDP 遥测 |
| `health.py` | 计时统计、STATUS 报文、看门狗、日志 |
| `main_hcv.py` | 主循环和状态机 |

### 1.2 主循环（单线程，事件驱动）

```
loop:
  img, t_cap = camera.snapshot(CHN0)        # 取最新帧，记录拍摄时间
  markers.update(img)                       # 每帧都做（窄窗口搜索）
  meas = detector.detect(img, roi, pred)    # 返回候选位置 u（亚像素）、质量
  u_c  = geometry.compensate(u, markers)    # 倾斜/平移补偿
  x    = geometry.lut(u_c)                  # 换算成 mm
  trk  = tracker.step(x, t_cap, meas.q)     # 门控、滤波、速度
  uart.send(BALL(trk, t_cap, age=now-t_cap))
  uart.poll_rx()                            # RUN_INFO，非阻塞
  every 1/2 s: uart.send(STATUS); telemetry.event(...)
  every N frames: telemetry.send(...)       # 抽帧发送，不阻塞
  health.tick(); gc 按受控节奏执行
```

图传由硬件把 CHN1 绑定到编码器，尽量不经过 Python 主循环（ADR-09）。

### 1.3 延迟预算（目标值，由 EXP-09 实测）

| 环节 | 预算 |
|---|---|
| 曝光（短曝光） | ≤ 4ms（取曝光时间的一半计） |
| 读出 + ISP + 送到内存 | ≈ 1 帧（90fps 时约 11ms） |
| snapshot 开销 | ≤ 2ms |
| 标记 + 检测 + 补偿 + 映射 + 跟踪 | ≤ 4ms（p95） |
| UART 发送 19 字节（115200） | 1.65ms |
| **合计** | **≈ 20–25ms**（指标 M5：P95 ≤ 35ms） |

对比：调研中 YOLO 方案的延迟约为 50–150ms【调研#1】。

## 2. 几何分析：为什么必须补偿摆杆倾斜

设摄像头在摆杆中心正上方高 H 处俯拍，摆杆绕左端合页（x = −125mm）倾斜 θ 角。摆杆靠近摄像头的部分会被"放大"，于是同一个钢球在图像上的位置会偏移。按理想针孔模型计算的测量误差（mm）如下：

| H | θ | x=−100 | −50 | 0 | +50 | +100 |
|---|---|---|---|---|---|---|
| 200mm | 3° | −0.7 | −1.1 | −0.2 | 2.2 | **5.9** |
| 200mm | 6° | −1.5 | −2.5 | −0.7 | 4.0 | **11.9** |
| 300mm | 6° | −1.0 | −1.8 | −0.7 | 2.2 | **7.2** |
| 300mm | 10° | −1.9 | −3.5 | −2.1 | 2.7 | **11.0** |
| 300mm | 20° | −4.5 | −9.6 | −8.8 | −0.7 | **16.3** |

调研显示，实际比赛中摆杆倾角可达十几到二十几度【调研#7】。**不补偿的话，误差会超过 1cm 的允许值。**

补偿方案对比（H=300mm、θ=6°时的最大误差）：

| 方案 | 最大误差 |
|---|---|
| 不补偿 | 7.2mm |
| 两端 2 个标记 + 线性归一化 | 4.4mm（中段反而变差，因为透视变换不是线性的） |
| 3 个标记（−110、0、+110）+ 分段线性 | 1.1mm |
| **3 个标记 + 一维射影变换拟合** | **0.03mm**（θ=20° 时也 < 0.35mm） |

结论：**在摆杆槽外的边沿上贴 3 个参考标记，每帧检测，用一维射影变换做补偿。**（理想模型的结果，实际效果由 EXP-08 验证。）

## 3. 决策记录

### ADR-01 测量在车上的 K230 完成，而不是交给场外笔记本

- **备选**：(a) K230 在车上完成测量；(b) 把视频传给笔记本，由笔记本计算后再回传。
- **正方（a）**：没有无线链路的延迟和抖动；不依赖 WiFi 的可靠性；符合"行驶中不得遥控"的规则（笔记本参与闭环，就有被认定为遥控的风险）。
- **反方（a）**：K230 上跑 MicroPython，开发和调试比电脑麻烦。
- **反驳**：必要的图像操作都有 C 实现（find_blobs、ulab 等）；而且算法核心可以在电脑上单元测试（ADR-10）。
- **裁决**：选 (a)，**不可推翻**（规则风险）。

### ADR-02 K230 只做测量，控制放在 MCU

- **备选**：(a) K230 输出位置，MCU 运行 PID；(b) K230 直接控制舵机或步进电机。
- **正方（a）**：分工清楚，CV 组和控制组可以并行开发；MCU 是硬实时的，而 MicroPython 有 GC 停顿；MCU 本来就要管小车和摆杆机构。
- **反方（a）**：多一跳 UART，大约增加 2ms 延迟。
- **反驳**：2ms 只占预算的 10% 左右（§1.3）。
- **裁决**：选 (a)。
- **推翻条件**：如果实测 UART 环节成为延迟瓶颈（>5ms），或者 MCU 资源不够，再重新评估。

### ADR-03 摄像头刚性固定在车身上俯拍，用 3 个参考标记做补偿

- **备选**：
  - (a) 固定在车身上，在摆杆中心正上方俯拍，加参考标记补偿；
  - (b) 装在摆杆上，随摆杆一起转动；
  - (c) 从合页一端斜着看过去；
  - (d) 固定在车身上，不做补偿，只把摄像头装高一些。
- **正方（a）**：摄像头的质量不加在摆杆上，不影响执行机构；画面稳定，评委看着舒服；参考标记**同时**能补偿倾斜、支架振动和安装微小移位。
- **反方（a）**：需要贴标记（存在规则理解风险），每帧要多检测 3 个标记，多花一些算力。
- **（b）的理由**：摄像头和摆杆相对静止，倾斜误差从原理上就不存在。
- **（b）的问题**：支架和摄像头装在摆杆上，转动惯量增大约 1 倍，执行机构负担变重；支架自己晃动会直接变成测量误差；FPC 排线要反复弯折；画面跟着摆，评委看着不舒服。
- **（c）的问题**：远端分辨率低，透视不均匀，照明也难做。
- **（d）的问题**：§2 已经算过，H=400mm、θ=10° 时误差仍有 7mm，而且支架太高容易晃。
- **裁决**：选 (a)。安装高度 H 由 EXP-03 实测的视场角决定（初步估计在 200–350mm 之间）。
- **推翻条件**：如果 EXP-08 测得补偿后误差在 |θ|≤6° 时仍大于 3mm，或者标记检测不稳定（漏检率 >1%），就改为在 RUN_INFO 中加入 MCU 回传的摆杆角度做几何补偿；如果这样还不行，再评估方案 (b)。
- **待全队确认**：标记贴在槽**外**边沿，不在槽内，不影响摩擦。我们判断这不违反规则，但需要全队一致同意（见 07）。确认之前，先用摆杆两端的挡片（防滚落挡片）作为天然标记，加上中心点的一个小标记作为备选。

### ADR-04 找球：传统 CV，同时实现两种检测器，YOLO 只作后备

- **备选**：
  - (A) 阈值 + 斑点（find_blobs）；
  - (B) 列剖面 − 背景基线（一维方法）；
  - (C) YOLO/CNN（KPU 推理）；
  - (D) Hough 圆检测。
- **事实**：
  - 钢球的外观取决于光照：补光直射时有很亮的高光【调研#2，亮阈值方案】，漫射环境下比白色管子暗【调研#2，暗区方案】。
  - 强反光会让候选目标暴增，管子边缘和接缝会产生误检【调研#3】。
- **(A) 的优点**：C 实现，速度快；在 CanMV 上用法成熟。**缺点**：固定阈值对光照敏感，高光会把一个球分裂成几块。
- **(B) 的优点**：钢球只能沿槽一维运动，剖面方法天然契合这一点。它不依赖亮还是暗（取的是偏离背景的绝对值），对光照的整体变化不敏感，还能做到亚像素精度。**缺点**：需要背景基线，而摆杆移动或光照变化时基线会失配；需要做在线更新。
- **(C) 的优点**：对光照的鲁棒性好。**缺点**：调研中这类方案的延迟有 50–150ms【调研#1】；要采集和标注数据、训练模型，工作量大；检测框中心的精度只有几个像素。
- **(D)**：慢，在小目标和反光条件下不稳定。不采用。
- **裁决**：(A) 和 (B) 都实现，接口统一，由 EXP-06 的数据选出默认检测器，另一个作为运行时的交叉校验或备份。(C) 只在 (A)(B) 都无法满足 M6 时启用。
- **推翻条件**：在补光条件下（L2），(A) 和 (B) 都达不到 M6（有效帧 ≥99.5%、误检 ≤0.05%）。这时先改进补光和管子颜色；仍然不行，再启用 (C)。

### ADR-05 检测通道用小图高帧率，sensor 模式由实验确定

- **备选**：sensor 用 1280×720@90 或 1280×960@60；检测通道缩小到大约 640 宽，或用硬件裁剪只取管子条带。
- **正方**：25cm 的摆杆画在 640 像素宽的图上，大约 0.45mm/px，加上亚像素精度已经远远够用。小图更快，留下余量给图传。
- **反方**：图越小，参考标记越小（5mm 宽的标记约 11px），对高光也越敏感。
- **裁决**：默认 sensor 1280×720@90，检测通道 640×360 灰度，ROI 裁成管子条带（宽约 640px，高约 40–70px）。如果 sensor 支持按通道硬件裁剪【调研#3】，就优先用硬件裁剪。最终由 EXP-01 和 EXP-05 决定。
- **推翻条件**：EXP-01 显示 90fps 模式不稳定（p99 帧间隔大于 2 倍标称值），或者图传通道无法同时工作，就改用 60fps 模式。

### ADR-06 对外只输出物理单位 mm；标定用钢球摆在已知刻度上的端到端方法

- **背景**：大多数队伍输出像素，控制参数也用像素调，摄像头一挪动就全部失效【调研#4、#5】。
- **备选标定方法**：
  - (a) 用磁铁把钢球吸在已知刻度处，记录像素位置，建立分段线性表；
  - (b) 拍一张图，在图上点击刻度线位置【调研：树莓派队】；
  - (c) 先标定相机内参，再加几何模型。
- **(a) 的优点**：**端到端**。高光偏移、照明不对称、钢球和刻度不在同一高度带来的视差，统统都被吸收进标定表。**缺点**：需要人工摆放，约 3–5 分钟；人读刻度有约 ±0.5mm 的误差。
- **(b) 的优点**：快，不用摆球。**缺点**：吸收不了检测器本身的偏差。
- **(c)**：需要精确测量摄像头外参，操作麻烦，安装误差会直接变成系统误差。
- **裁决**：主方法用 (a)：25 个点（−120 到 +120mm，每 10mm 一个），快速复核用 3 个点。(b) 作为可选辅助，用来交叉检查。标定文件要绑定相机配置指纹，配置变了就拒绝加载【调研：树莓派队】。
- **为什么用磁铁**：钢球是铁磁性的，小磁铁放在管子**外壁下方**就能把球定住，槽内不留任何东西，不违规。磁铁只在标定和静态测试时使用。（EXP-07 会验证磁铁会不会让球的位置产生偏差。）
- **推翻条件**：EXP-07 显示 25 点不够（交叉验证误差 >1mm），就加密标定点；显示 13 点就够了，就减少标定点，缩短标定时间。

### ADR-07 主动漫射补光；能锁定曝光就锁定

- **备选**：(a) 只用环境光；(b) 加漫射 LED 补光，曝光时间固定；(c) 加遮光罩，完全封闭。
- **正方（b）**：现场光照不可控（顶灯、窗户、人走动投下的影子），自己的光源占主导，结果才稳定；短曝光还能减少运动模糊。
- **反方（b）**：钢球是镜面，LED 会在球上和管子内壁上产生高光，可能更糟。
- **反驳**：使用漫射（加柔光片、光源较大、从侧上方照射），避免点光源直射；这一点由 EXP-04/05 用数据验证。
- **（c）的问题**：可能挡住评委的视线，结构上也麻烦。可以作为局部挡光的选项保留。
- **裁决**：选 (b)。曝光能否锁定由 EXP-02 确认；锁定不了，算法就用相对阈值和自适应基线（检测器 B 天然支持）。
- **推翻条件**：EXP-05 显示补光反而降低了检出质量，就改用环境光加算法自适应。

### ADR-08 串口用二进制定长帧 + CRC-8，默认 115200

- **备选**：(a) ASCII 文本行；(b) 二进制帧带 CRC。
- **正方（b）**：解析确定、不需要浮点运算、带宽小；有 seq、时间戳和有效位，能防止旧数据冒充新数据【调研#6】。调研中做得好的方案都采用了类似的结构【调研：doinnothin、XHZ、树莓派队】。
- **反方（b）**：人眼读不懂，调试不方便。
- **反驳**：我们提供串口嗅探工具，把帧解码成文本；同时提供 C 解析库和测试向量（P1-T03）。
- **波特率**：19 字节 × 90Hz ≈ 1.7kB/s，只占 115200 带宽的 15%，单帧发送时间 1.65ms。提高到 921600 只能节省约 1.4ms，却会增加线缆和电平方面的风险。默认 115200，可配置。
- **裁决**：选 (b)，具体格式见 ICD。

### ADR-09 图传：K230 硬件 H.264 + RTSP + WiFi，叠加信息在笔记本端做；准备一套独立图传作后备

- **备选**：
  - (a) K230 硬件 H.264 编码 + RTSP；
  - (b) K230 用 Python 推 MJPEG 或 UDP-JPEG；
  - (c) 独立图传（5.8G 模拟图传加采集卡，或者第二块 K230、ESP32-CAM）。
- **事实**：
  - K230 走 RTSP 时，VLC 默认缓存会造成 1–2s 延迟，把缓存调到 200ms 后约 200ms【调研#10】。
  - 用 Python 逐包复制数据会拖慢主循环；Python 推 MJPEG 或 UDP-JPEG 的实测结果参差不齐（2–15fps）【调研#10】。
  - 有队伍用第二块 K230 专门做图传【调研：AkezI-T】。
- **正方（a）**：只用一个摄像头；编码由硬件完成，CPU 占用低；画质高（评委要看清刻度）。
- **反方（a）**：会和检测争抢资源（内存带宽、ISP 通道）；2.4G WiFi 在赛场可能很拥挤。
- **画面叠加放在哪里做**：
  - 放在 K230 上：要么在 CPU 上画（破坏零拷贝路径），要么用 OSD/WBC 硬件叠加（有队伍尝试过，复杂度高）。
  - 放在笔记本上：用遥测数据画叠加，**K230 零负担**。录像同时保存原始码流和 CSV，回放时再叠加。
- **网络模式**：首选 K230 开 AP，笔记本直连，现场不需要路由器，也不需要额外的封存设备。如果 AP 不稳定，再改用便携路由器（这时路由器也要一起封存）。
- **裁决**：(a) 为主，叠加在笔记本端做（K230 端 OSD 作为可选实验）；(c) 作为后备，P4 之前由队员先询价、准备好。(b) 不采用。
- **推翻条件**：EXP-12 显示开启推流后检测帧率下降超过 10%，或者延迟增加超过 5ms，或者 10 次录像中有缺段，或者显示延迟大于 500ms。这时先尝试降低码率、帧率和分辨率；仍然不行，就切换到方案 (c)。

### ADR-10 开发语言：CanMV MicroPython；算法核心可以在电脑上测试

- **备选**：(a) MicroPython（CanMV）；(b) 用 RT-Smart SDK 写 C。
- **正方（a）**：开发快，例程多；需要的图像操作都有 C 实现。
- **反方（a）**：GC 停顿和解释器开销不可控。
- **对策**：主循环里不分配内存；手动控制 GC；每一步计时；EXP-05 测出完整的耗时分布。
- **裁决**：选 (a)。
- **推翻条件**：EXP-05 或 EXP-09 显示，Python 开销导致 p95 处理时间大于 8ms，或者帧率达不到 60Hz，并且优化也无效。

### ADR-11 速度估计在 K230 上做，同时提供原始位置

- **理由**：K230 有精确的拍摄时间戳，最适合按真实 dt 做卡尔曼滤波。直接差分会放大噪声【调研：doinnothin】。
- **同时输出 pos_raw**：控制组如果想自己滤波，可以只用原始值。
- **跟踪器的边界**：只做"测量层面"的滤波（门控、平滑、外推最多 3 帧），**不做控制层面的预测**。延迟补偿由控制组根据我们实测的延迟来设计。

### ADR-12 遥测走 UDP，只往外发

- **理由**：笔记本需要画曲线、存 CSV，用于调试和写报告。
- **合规**：K230 只接受 HELLO 登记包，用来知道发给谁，不接受任何其他网络命令（ICD §5）。
