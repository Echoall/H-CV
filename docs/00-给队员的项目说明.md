# 给你的项目说明（大白话版）

> 这份文档是写给你的，不需要懂代码。看完以后你应该知道：我们要做什么、为什么这么做、分几步走、你要做什么、要和别的组商量什么。
> 技术细节都在其他文档里，那些是给 Codex 和控制组看的。

---

## 1. 一句话：CV 组要干什么？

**当好整个系统的"眼睛"**：盯着摆杆上的那颗钢球，每秒报告 60–90 次"球在哪儿、往哪边滚、滚多快"，误差控制在 2 毫米以内。同时把画面实时传到场外的笔记本上，录下来给评委看。

题目 100 分里有 **79 分**直接靠这双眼睛：

- 要求 3–6 一共 73 分。控制组是靠我们报的位置来调摆杆的，眼睛看不准，手就不可能稳。
- 要求 1 的图传 6 分，完全归我们组。

## 2. 整个系统像什么？

```
 摄像头 = 眼球      K230 = 视觉神经（看懂画面）      控制组 MCU = 小脑（决定怎么动）      摆杆电机 = 手
   │                    │                                 │
   └── 拍到画面 ────►  算出"球在 +32.5mm，         ──►  决定"摆杆往左倾 2°"  ──►  球滚回中间
                        正以 80mm/s 向右滚"
                        │
                        └── 同时把画面通过 WiFi 传给场外笔记本（给评委看、录像）
```

**分工的边界**：我们只负责"看准、报准"，**不负责"怎么动"**。怎么动是控制组的事。
这样两个组可以同时开工，互不卡脖子。

## 3. 我们的方案（6 个关键选择，以及为什么）

我把网上能找到的 15 个同题开源作品都翻了一遍，其中有省一、省二、省三等奖的队伍。下面每个选择，都考虑过"别人在这儿摔过什么跤"。

### ① 用"传统图像算法"找球，而不是 AI 模型（YOLO）

- **别人怎么做**：大多数队伍用 YOLO（一种 AI 识别模型）。它的毛病是**慢**：从拍到画面到报出位置，要 50–150 毫秒。控制组只好去"猜"球的未来位置来弥补。
- **我们怎么做**：钢球只能在槽里一维地滚来滚去，所以只要在一条细长的区域里找"和背景不一样的那一小段"就行了，这个用传统算法就能做到。目标延迟在 **35 毫秒以内**，比 YOLO 快好几倍。
- **留后路**：实验如果证明传统方法在某些光照下不可靠，再启用 AI 模型作后备。

### ② 两种找球方法一起做，用实验数据决定用哪个

- **为什么**：调研发现，同一颗钢球，有的队伍拍出来是**亮的**（灯直射时产生高光），有的队伍拍出来是**暗的**。到底是哪种，取决于打光。
- 所以我们不提前拍板，两种方法都实现，再用真实的拍摄数据比一比，选更稳的那个。

### ③ 报给控制组的是"毫米"，不是"像素"

- **别人踩的坑**：很多队伍报的是"球在画面第几个像素"，控制组的参数也是按像素调的。摄像头被碰歪一点，所有参数就全废了。有一支省三队伍就是在赛场上支架松了，第三题才失败的。
- **我们怎么做**：先做"标定"，把球放在已知的刻度上，让系统记住"刻度 +30mm 对应画面的哪个位置"，然后统一报毫米。
- 我们还准备了一个 **1 分钟快速复核**：比赛前把球放在 0、+5cm、−5cm 三个位置，系统自己判断"标定还准不准"。不准就不上场，先重新标定（大约 5 分钟）。

### ④ 摆杆倾斜时，"近大远小"会让位置算错，要补偿

- **问题**：摆杆一倾斜，靠近摄像头的那一端就会在画面里显得"变大"，球的位置就算偏了。我算过，倾斜 6° 时误差可能有 7–12 毫米，**超过题目允许的 1 厘米**。而调研显示，别的队伍比赛时摆杆倾角能到十几到二十几度。
- **我们怎么做**：在槽外的边沿上贴 3 个小黑块，分别在 −11cm、0、+11cm 处，作为"参考尺子"。系统每一帧都看这 3 个黑块被拉伸、移动了多少，然后把球的位置换算回来。理论计算表明，这样可以把误差降到 0.3 毫米以下。
- ⚠ **需要全队确认**：规则只禁止往"槽内"贴东西，我们是贴在"槽外边沿"上，应该不违规。但这件事要大家一起读一遍规则，确认后再贴。

### ⑤ 自己带补光灯

- 比赛场地的灯光我们控制不了，可能有窗户进来的光，也可能有人走过投下影子。自己带一组柔和的 LED 灯，让画面的亮度主要由我们自己决定，结果就稳定。
- 灯具体怎么摆，用实验来定。

### ⑥ 图传：K230 直接用 WiFi 发视频，笔记本负责显示、录像和叠字

- K230 自带硬件视频压缩，用它发高清画面（目标 1280×720），评委能看清刻度。
- K230 自己开一个 WiFi 热点，笔记本直接连上去，现场不需要路由器。
- "球在 +32.5mm"这类文字，叠加在**笔记本端**的画面上，K230 就不用为画字多费力气。
- 小车按下启动键后，笔记本会**自动开始录这一次测试**，测试结束自动停止，文件名里带着测试编号，回放时一找就到。
- **留后路**：如果实验发现 WiFi 图传会拖慢找球，或者在赛场上不稳定，就换成一套独立的图传设备。**需要你提前询价**（见第 5 节）。

## 4. 分几步走？每一步你会看到什么？

| 阶段 | 做什么 | 做完后你会看到 | 你需要帮忙做的 |
|---|---|---|---|
| **P0 摸底** | Codex 学会操控 K230，并实测摄像头的能力（帧率、视野多宽） | 一份报告，写着"摄像头装多高合适"，可以直接交给结构组 | 用万用表测一个电压；把摄像头对着网格纸，放在 3 个不同高度拍照 |
| **P1 拍数据、做协议** | 在各种光照下拍钢球；把串口协议做好 | 钢球照片数据集；控制组可以拿去用的"通信代码包" | 搭一个临时的摆杆和支架；按提示摆球、开关灯 |
| **P2 测得准** | 做两种找球方法、标定、倾斜补偿 | 静止时误差 ≤ 2mm 的实测报告 | 摆球、垫角度、贴 3 个小黑块；亲手做一次标定 |
| **P3 实时跑起来** | 每秒 60–90 次报位置，测清楚延迟 | "CV v1 交付包"，交给控制组联调 | 接一个 LED 小灯（用来测延迟）；让球从斜面滚下来 |
| **P4 图传** | 实时画面、自动录像、回放、曲线 | 笔记本上能看画面、自动录像的软件 | 准备一台要被封存的笔记本；拍照测延迟 |
| **P5 上车、备赛** | 装上真车跑；准备比赛当天的操作手册 | 一份《比赛当天操作手册》和一份设计报告素材 | 和全队一起跑车测试；按手册模拟一次比赛 |

**每个阶段结束时**，Codex 会把成果传到 GitHub，然后由我来验收。验收时我会自己重新计算一遍关键数字，不是只看 Codex 写的结论。

## 6. 你、我、Codex 怎么配合？

```
   我（Claude，经理）             你（队员）                     Codex（执行）
   写方案、写任务书    ──推到 GitHub──►
                                 对 Codex 说：
                                 "按 AGENTS.md 执行 P0"   ──►   写代码、上板实验
                                                                遇到要动手的步骤 ──► 你按提示操作
                                                                做完推到 GitHub（分支 codex/P0）
                                 对我说："验收 P0"    ◄──
   拉代码、重算数字、
   写验收意见  ──►  通过：合并，进入下一阶段
                    不通过：写整改单，你转告 Codex 去改
```

你只需要说三种话：

1. 对 **Codex**：「请阅读 AGENTS.md，执行 tasks/ 里的 P0 阶段。」
2. Codex 让你动手时：照着它的编号清单做，**做完再告诉它**。没做的步骤不要说做了。
3. 对 **我**：「Codex 已经交了 P0，请验收。」（如果 Codex 建了 PR，就把 PR 链接一起发给我。）

如果实验结果推翻了原来的方案，这在计划之内，也是我们安排这么多实验的原因。我会修改方案，并写清楚为什么改。

## 7. 你要和其他组商量的事（精简版）

完整清单在 [07-对接参数清单.md](07-对接参数清单.md)。最重要的是下面这些：

**和控制组**：

1. 用哪块单片机、哪个串口？电平**必须是 3.3V**。
2. 波特率定为 115200，通信格式按我们的协议文档。我们会提供现成的 C 代码和电脑上的模拟器，他们不用等我们做完就能先调。
3. 坐标方向：摆杆中心是 0，朝**电机那一端**是正方向，单位是 0.1 毫米。
4. 他们要做的保护：100 毫秒收不到数据，就让摆杆回到水平。
5. 摆杆最大会倾斜多少度？（我们要按这个角度做测试。）
6. 标定时，能不能把摆杆锁在水平位置？
7. 要求 6「任意位置」的做法：开跑前取 20 帧位置的平均值，作为目标位置。
8. 小车开始和结束测试时，给 K230 发一个消息（用于自动录像）。

**和结构组**：

1. 摄像头装在车身上，在摆杆正上方往下拍，**不要装在摆杆上**。高度等 P0 测完再告诉他们，支架要能调高度、调好后能锁死。
2. **用螺丝固定，不要只用热熔胶**（有队伍就是因为热熔胶松了才输的）。
3. 管子尽量用白色的。
4. 槽外边沿贴 3 个小黑块（等全队确认规则后再贴）。
5. 补光灯装在摄像头两边，加柔光纸。
6. 整个支架不能超出车身 35×25cm 的范围。

**和硬件 / 电源组**：

1. K230 的供电：通过 Type-C 口供 5V。建议加一个独立的 5V/3A 降压模块，从电池取电（具体待查幻尔手册）。
2. 所有板子必须**共地**。
3. K230 开机大约需要 20–30 秒。小车要等 K230 报告"准备好了"，才允许按启动键。

**全队一起定的事**：

1. 贴参考标记是否违规？（建议一起读规则，然后签字确认。）
2. 准备一台会被封存的接收设备。

## 8. 关键数字速查

| 项目 | 目标 |
|---|---|
| 静止时的位置误差 | ≤ 2 毫米（题目允许 10 毫米） |
| 静止时的抖动 | ≤ 0.3 毫米 |
| 摆杆倾斜 6° 时的误差 | ≤ 3 毫米 |
| 每秒报告次数 | ≥ 60 次（目标 90 次） |
| 从拍到画面到报出位置的时间 | ≤ 35 毫秒 |
| 找不到球的帧 | ≤ 0.5% |
| 图传延迟 | ≤ 0.5 秒 |
| 开机到准备好 | ≤ 30 秒 |
| 完整标定 / 快速复核 | ≤ 5 分钟 / ≤ 1 分钟 |

## 9. 名词小词典

| 词 | 意思 |
|---|---|
| K230 | 我们用的视觉处理板（**幻尔 CanMV K230**） |
| MCU / 单片机 | 控制组用来控制小车和摆杆的芯片 |
| UART / 串口 | K230 和单片机之间的两根通信线 |
| 帧 | 摄像头拍的一张照片；"90 帧每秒"就是每秒拍 90 张 |
| 延迟 | 从事情发生到我们报告出来的时间差 |
| 标定 | 让系统记住"画面上的某个位置对应摆杆上的多少毫米" |
| ROI | 画面中我们关心的那一小块区域（这里就是槽里那一条） |
| 图传 | 把画面无线传到场外 |
| RTSP | 一种视频直播的传输方式 |
| AP 模式 | K230 自己开一个 WiFi 热点 |
| 卡尔曼滤波 | 一种"让数字更平稳、顺便算出速度"的数学方法 |
| PR | GitHub 上的"合并请求"，就是 Codex 提交成果、等我验收的地方 |
| CR | 变更请求：Codex 发现方案有问题时提出的修改建议 |
