## 1. 这一步做了什么（一句话）

Codex 写了一套"协议代码"。K230 用它把球的位置**打包**成一帧一帧的数据，控制组的单片机用它把收到的字节**拆包**还原成数字。这套代码要交给控制组直接用。

一共有两个版本：
- **Python 版**：给 K230 和电脑用。K230 跑的是 MicroPython，电脑上用它来写测试和调试工具。
- **C 语言版**：给控制组的单片机用。单片机上一般跑不了 Python，只能跑 C。

还有两个辅助工具：
- **嗅探器**：把 USB 转串口线夹到线上，"偷听"线上传的数据，实时翻译成人能看懂的数字。
- **MCU 模拟器**：在电脑上假装自己是控制组的单片机，提前把我们这一侧测完，不用等控制组。

---

## 2. 打包（编码）：很简单

把数字按 ICD 规定的顺序，一个字节一个字节地排好，前面加帧头 `A5 5A`，后面算一个 CRC。打包只是"按格式填表"，不容易出错。

**小端是什么意思？** 一个 16 位整数（比如位置 325 = 0x0145）要占 2 个字节。"小端"是指**低位字节放在前面**：先发 `45`，再发 `01`。两边说好用同一种顺序就行。我们的 K230 和常见的单片机（STM32 之类）内部本来就是小端，处理起来最省事。

---

## 3. 拆包（解析）：真正的难点

单片机收到的不是"一帧一帧"的数据，而是**一个字节接一个字节的流**，像水龙头里流出来的水，中间没有分隔。它得自己判断：一帧从哪里开始、到哪里结束、这一帧有没有在传输中出错。

### 3.1 状态机：边收边判断

解析器就像一个流水线上的检查员，手里有一张检查单，每收到一个字节就往下核对一步：

```
等 A5 ──收到A5──► 等 5A ──收到5A──► 读长度 LEN ──► 读 MSGID ──► 读剩下的内容 ──► 读 CRC ──► 校验
  ▲                 │不是5A                                                              │
  └─────────────────┴──────────────────────── 任何一步不对，就回到开头 ◄────────────────┘
```

这种"现在处于哪一步、收到什么就跳到哪一步"的写法叫**状态机**。单片机在串口**中断**里调用它：每收到一个字节，硬件就打断主程序，喂给它一个字节。

### 3.2 为什么数据会出错

串口线有可能受到干扰，比如电机的电磁噪声或者接触不良，结果某个字节的某一位从 0 变成 1。CRC 就是用来发现这种错误的。对我们的帧来说，CRC-8 能 100% 发现"错 1 位"的情况。

**发现错误以后怎么办？这次返工的核心问题就出在这里。**

---

## 4. 这次返工的故事（最值得学的部分）

### 4.1 第一版的毛病

第一版 C 解析器的逻辑是：读到 LEN 以后，**先按 LEN 把后面的字节全部读完，再去检查对不对**。

想象线上一个 LEN 字节被干扰了：本来是 `0F`（15），变成了 `FF`（255）。解析器信以为真，接下来老老实实收了 255 个字节，收完才发现"不对，这一帧长度和 MSGID 对不上"，然后整帧扔掉。

问题在于，这 255 个字节里**其实装着后面 13 帧完全正常的数据**，它们被一起扔掉了。

我把它的 C 代码逐行翻译成 Python 跑了一遍，结果是：

| 损坏方式 | 第一版丢了哪些帧 |
|---|---|
| 不损坏 | 无 |
| 第 10 帧截掉 5 字节 | 10、11 |
| 第 10 帧 LEN 变成 0xFF | **10 到 23，共 14 帧** |

14 帧 ÷ 90 帧/秒 ≈ **0.15 秒**。在这 0.15 秒里，控制组完全不知道球在哪。球每秒能滚 300 mm，0.15 秒就是 45 mm，足够让球从摆杆上掉下去。

### 4.2 怎么修

修复后的做法有三点：
1. **尽早检查**：一读到 MSGID 就知道这种消息应该多长，长度不对**立刻**放弃，不再傻等。
2. **给长度设上限**：我们最长的帧也就三十几个字节，LEN 超过 32 直接判为错误。
3. **回头重找**：出错时，不把已经收进来的字节全部扔掉，只扔掉第 1 个字节，然后在剩下的字节里重新找 `A5 5A`。下一帧的开头很可能就藏在里面。

类比：你在听一段广播，突然听到一句乱码。旧办法是捂住耳朵数 255 秒再接着听，新办法是马上跳过这个字，接着听下一句。

另外还修了一个问题：旧版在中断里临时开了一个 256 字节的数组。单片机的中断栈（中断程序能用的临时内存）可能只有 512 字节到 1 KB，这样做很危险。新版用一个固定的 36 字节小缓冲，整个解析器只占约 560 字节内存。

### 4.3 修完以后怎么证明是真的好了

我没有只看 Codex 的报告，而是自己另写了一个 C 测试程序：

| 损坏方式 | 修复后丢了哪些帧 |
|---|---|
| 截断 / LEN=FF / 内容翻一位 / 帧头翻一位 / MSGID 被改 | **都只丢第 10 帧** |
| 随机测试：连发 10575 帧，随机损坏约 2% | 完好的 10357 帧**一帧不丢**，损坏的帧**没有一帧被误收** |

### 4.4 这件事教会我们什么

1. **测试不能"太温和"。** Codex 第一版也写了模糊测试，但里面只有 20 帧好数据、彼此隔得很远，坏数据只有 1 帧，而且只坏了 CRC。这样的测试永远测不出"连丢 14 帧"的问题。好的测试要**模仿最坏的真实情况**：帧首尾相接，各个位置都可能被破坏。
2. **"测试全部通过"不等于"没有问题"**，还要看测试本身测了什么。
3. **交叉验证**：做的人和验的人分开，验的人自己动手重测。这就是我们分 Manager 和执行两个角色的原因。

这个故事很适合写进设计报告，也很适合讲给评委听："我们怎么保证通信可靠"。
