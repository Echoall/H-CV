# 2026 H 题同题开源作品调研（视觉相关）

> 调研日期：2026-11-19。以下只摘录与 CV 有关的事实和教训，均标注了出处。各仓库自述的成绩、数据**未经我们复现**，只作为参考。
> 调研目的：不闭门造车。凡是别人踩过的坑，我们的方案都要有对应的措施。

## 2. 结论：别人的做法与教训 → 我们的对策

| # | 观察到的现象（出处） | 我们的对策（写在哪里） |
|---|---|---|
| 1 | 多数队伍用 YOLO，延迟 50–150ms，只好在 MCU 端预测好几帧来补偿（省一队、doinnothin） | 主方案用传统 CV（可以做到 <30ms）；YOLO 只作后备（ADR-04） |
| 2 | 钢球有时亮（补光直射产生高光，AkezI-T）、有时暗（漫反射环境，kevin） | 不预设亮暗；同时实现"阈值斑点"和"背景差剖面"两种检测器，靠 EXP-05、EXP-06 的数据选择（ADR-04） |
| 3 | 强反光会让候选目标暴增，管子边缘和接缝会误检（AkezI-T、kevin） | 用漫射补光 + 限制候选数 + 窄 ROI + 跟踪门控（04-算法规格） |
| 4 | 坐标用像素，PID 也用像素调；摄像头一挪动，所有参数都失效（省一队、AKO-J） | **对外只输出 mm**，标定吸收安装差异；提供 1 分钟快速复核流程（ICD、04 §5） |
| 5 | 机械松动毁掉了标定（AKO-J 复盘） | 标定文件绑定相机配置指纹；每次搬运后必须快速复核，不通过就禁止开跑（04 §5.4） |
| 6 | 协议没有序号和时间戳，旧数据冒充新数据（tao 复盘） | 每帧带 seq、拍摄时间戳、帧龄、有效位和 CRC；MCU 端设超时（ICD §3） |
| 7 | 摆杆倾角可达十几到二十几度（省一队） | 倾斜引起的透视误差必须补偿：用摆杆上的参考标记，以及（可选的）MCU 回传的摆杆角度（ADR-03、04 §6） |
| 8 | 摆杆两端检出率低（树莓派队） | 验收必须覆盖 ±12cm 两端；补光要沿杆均匀（06） |
| 9 | 只标定了一半行程（AkezI-T） | 标定必须覆盖全程 −12~+12cm（04 §5） |
| 10 | VLC 默认缓存导致 1–2 s 延迟；Python 逐包复制会拖慢主循环（树莓派队的 K230 实测） | 走硬件编码、零拷贝推流；接收端用低延迟参数（05） |
| 11 | 上位机在任务开始和结束时自动录像，很好用（AkezI-T） | 采用：MCU 把任务状态发给 K230，K230 转发给上位机，上位机据此自动分段录像（ICD §4、05） |
| 12 | TX 空闲 0V、引脚映射出错（AKO-J） | P0 必须做串口回环和电平测量（P0-T03） |
| 13 | "任意指定位置"的常见做法：开跑前采 20 帧取平均，作为目标位置（省一队、doinnothin） | 写进对接文档，由控制组实现；我们保证静止时的噪声足够小（07） |
| 14 | 有队伍用 AI 智能体开发时，配了无线开发代理和 USB raw REPL 兜底（树莓派队、AKO-J） | Codex 的板卡访问方式必须脚本化并写进文档（AGENTS §5） |

## 3. 我们比现有作品多做的事

1. **端到端延迟实测**：用 LED 闪烁法测"曝光 → 串口发出"的真实延迟。调研到的作品要么没测，要么只测了处理时间。
2. **倾斜误差的定量实验和补偿**：其他队伍大多忽略了这一项。
3. **每个结论都有原始数据和可复现的脚本**，设计报告里的测试数据可以直接拿来用。
