# P1 数据与协议先行

**阶段目标**：

1. 采集真实的钢球外观数据，用来回答"钢球在画面里到底是什么样子、补光有没有用"。
2. 把协议做完，提前交给控制组，让他们不必等我们就能开始联调。

**本阶段需要的实物**：

- 摆杆样件：一段 25cm 的 4 分 PPR 管，按题目要求剖开，贴好刻度（白色管优先）
- 2–3 颗直径 1cm 的钢球
- 小磁铁：直径 5–10mm 的钕铁硼磁铁
- 临时摄像头支架：高度按 P0 给出的推荐值，可以调节
- LED 灯条和柔光纸（硫酸纸）
- 台灯和手机手电（用来制造不同光照）

**质疑要求**：外观数据要特别关注那些"我们没想到的情况"，例如：

- 管子内壁的高光条纹
- 刻度贴纸的反光
- 槽沿的阴影
- 两端挡片附近的画面
- 钢球上映出的摄像头或支架的倒影

## P1-T01 图像与序列采集工具、数据集格式

**目标**：能方便地从板上采集单帧图像和高帧率序列，并按统一格式存成数据集。

**步骤**：

1. 板上脚本 `k230/exp/cap_frames.py`，支持两种模式：
   - **单帧模式**：每次按提示采 N 帧，保存为无损格式（优先用 `.npy` 或原始的 `.bin`+`.json`；如果固件支持 PNG 或 BMP，也可以），同时保存检测通道图和 CHN1 全画面图。
   - **序列模式**：以全帧率把 K 帧（例如 300 帧）缓存到内存，之后再统一写盘，避免写卡拖慢采集。同时保存每帧的 `ticks_us`。
2. 电脑端 `tools/capture/`：
   - 发送命令启动采集；
   - 提示人工步骤（AGENTS §6）；
   - 自动取回文件；
   - 按 `datasets/README.md` 的格式整理。
3. 写 `datasets/README.md`，定义数据集格式：
   - 目录结构：`datasets/<数据集名>/<场景>/`
   - 每段数据配一个 `meta.json`，记录：光照编号、管子颜色、真值 x（mm，静态时填写）、摆杆角度、sensor 配置、曝光、日期、操作员备注
   - 大文件的管理规则：提交的样本要小；大文件用 Git LFS，或者只在仓库里记录存放位置和 SHA-256

**验收标准**：

- [ ] 单帧模式和序列模式都在板上跑通。
- [ ] 序列模式的实际采集帧率不低于 P0-EXP01 推荐配置帧率的 95%（附 ticks 统计）。
- [ ] 一个示例数据集（≥ 3 段）按格式提交。

## P1-T02 离线评测框架与合成图像生成器

**目标**：在电脑上就能评测检测算法，不必每次都上板。

**步骤**：

1. `tools/eval/`：读入数据集 → 调用检测器（和 `k230/hcv/` 是同一份代码，通过 `compat.py` 适配 numpy 和 ulab）→ 输出逐帧结果 CSV → 计算指标：误差统计、有效率、误检、耗时（电脑耗时只作参考）。
2. 合成图像生成器 `tools/synth/`，能生成"槽 + 球"的灰度图，可控制以下参数：
   - 球的位置、亮暗极性、高光大小和位置
   - 背景渐变、噪声
   - 接缝或划痕等干扰物
   - 标记位置
   - 透视倾斜（按 02 §2 的模型）

   生成器用来做单元测试，并回归测试检测器的边界情况。
3. 写 pytest：评测框架用合成数据跑通，指标计算正确（用手算过的小例子来验证）。

**验收标准**：

- [ ] `pytest -q` 通过。
- [ ] 用合成数据，生成器给出的真值和评测框架算出的误差统计一致（用"理想检测器"验证时，误差为 0）。

## P1-T03 协议库、测试向量、嗅探器、MCU 模拟器

**目标**：完整实现 ICD v1.0，交付给控制组。

**步骤**：

1. `protocol/python/hcv_proto.py`：编码和解码所有报文。要求同一份代码能在 CPython 和 MicroPython 下运行（只用 `struct`，不用 dataclass）。还要实现一个流式解析器：可以逐字节或逐块输入；遇到错误时重新同步；统计 CRC 错误和丢帧。
2. `protocol/c/hcv_proto.h/.c`：C99，不使用 malloc。包括流式解析状态机（输入一个字节，输出"是否解出一帧"）和各报文的结构体，并附一个 `example_mcu.c`，演示在 UART 中断里怎么使用。
3. `protocol/test_vectors.json`：包含 ICD §3.6 中的全部用例，再补充至少 20 个：边界值、INT16_MIN、seq 回绕、t_cap 回绕、未知 MSGID、LEN 异常。
4. 交叉测试：Python 编码的帧给 C 解码，C 编码的帧给 Python 解码，结果必须一致（`tests/test_c_protocol.py` 调用 gcc 编译）。
5. 模糊测试：随机字节流中混入合法帧，并加入随机的位翻转和截断。要求：
   - 不崩溃；
   - 所有完好的帧都能解出来；
   - 被破坏的帧，CRC 能拒绝；
   - 拒绝后能在下一帧重新同步。

   随机数种子要固定，以便复现。
6. 工具：
   - `tools/sim/uart_sniffer.py`：从 USB-TTL 读取数据，实时解码并打印，同时可以存成 CSV。
   - `tools/sim/mcu_sim.py`：在 PC 上扮演 MCU，按脚本发送 RUN_INFO 和 CMD（例如模拟"测试 5 开始 → 30s → 结束"），接收 BALL 帧，并统计帧率、丢帧和超时。
7. 写一份给控制组的说明 `protocol/README.md`：怎么接线、怎么用 C 库、怎么用模拟器自测，以及 MCU 端必须实现的保护（引用 ICD §3.1）。

**验收标准**：

- [ ] ICD §3.6 中的 6 个官方测试向量逐字节一致。
- [ ] 全部测试向量 + 交叉测试 + 模糊测试（≥ 10⁶ 字节）通过。
- [ ] 板上用 MicroPython 编码 BALL 帧，经串口回环（P0-T03 的接法）收回后解码一致，连续 10,000 帧（附日志）。
- [ ] `protocol/README.md` 写得足够清楚，控制组照着就能接入。

## P1-EXP04 钢球外观与光照数据集 🖐

**问题**（影响 ADR-04、ADR-07）：

- 钢球在画面里是亮还是暗？高光有多大？
- 补光是否有效？应该怎么摆放？
- 哪些地方容易误检？

**方法**：

1. 🖐 按 P0 给出的推荐高度，把摄像头临时架在摆杆样件上方，并按 04 §1 的要求对准。
2. 光照条件：L1–L5（06 §0）。对于 L2，再试 2–3 种补光摆法：
   - (a) 灯条在摄像头两侧，加柔光纸，斜向下 45° 照射；
   - (b) 灯条平行于摆杆，从侧上方照射；
   - (c) 正上方环形光（如果有条件）。
3. 每种条件下采集：
   - 静态：钢球用磁铁固定在 −120、−90、−60、−30、0、+30、+60、+90、+120mm 这 9 个位置，每个位置 30 帧；外加空槽 30 帧。
   - 动态：手动让球往返滚动 3 段，每段 300 帧（序列模式）。
4. 如果有不同颜色的管子，在 L2 下补采一组。
5. 计算以下指标：
   - 球与背景的对比度：球区和背景的平均灰度差，除以背景噪声；按位置统计。
   - 高光的面积和亮度；是否有饱和像素。
   - 背景（空槽）剖面的非均匀程度：标准差、梯度，以及接缝和刻度的位置。
   - L5 下的条纹（banding）幅度。
   - 两端（±120mm）的对比度和中间相比下降了多少。

**产出**：

- 数据集 `datasets/appearance_v1/`（按 P1-T01 的格式，大文件按规则处理）。
- 报告：每种条件的代表性截图，附原始数据。
- 结论：钢球的主要外观极性（亮或暗），以及它随条件怎么变化；推荐的补光摆法（附理由）；容易误检的位置清单。
- **给结构组的补光安装建议**。

**验收标准**：

- [ ] 5 种光照、2 种以上补光摆法的数据都已采集，并且标注完整。
- [ ] 给出推荐补光方案，以及"球区对比度 / 背景噪声"的量化对比表。
- [ ] 列出至少 3 个"潜在误检源"（可以是实际观察到的，也可以写"未观察到"），每个都附截图。

## P1-EXP05 板上处理耗时基线

**问题**（影响 ADR-05、ADR-10）：各种图像操作在 K230 上实际要花多少时间？

**方法**：用推荐配置的真实帧（从 EXP-04 的数据中选，或者实时采集），每项操作连续计时 1,000 次，统计 p50/p95/p99/最大值：

1. `snapshot`（检测通道）
2. 拷贝 ROI 子图，或者直接用 `roi=` 参数
3. `to_numpy_ref`（如果有）+ `ulab` 按 axis=0 求平均（640×48 的 ROI）
4. `ulab` 的累加和、盒式滤波、`argmax`（长度 640）
5. `find_blobs`（暗阈值和亮阈值各测一次，ROI 640×48）
6. `get_statistics` / `get_histogram`（ROI 内）
7. 3 个标记窗口的剖面计算
8. 3×3 线性方程组求解（射影补偿）+ 查表插值
9. `struct.pack_into` 打包 19 字节，加上 `uart.write`
10. `gc.collect()`：分别在主循环不分配内存和分配内存两种情况下测
11. `time.ticks_us()` 本身的开销

**产出**：耗时表、根据耗时估算的"单帧处理总预算"，以及 gc 策略建议。

**验收标准**：

- [ ] 11 项操作都有数据。
- [ ] 结论：按 02 §1.2 的主循环，单帧处理时间的 p95 估计是否 ≤ 4ms。超过的话，指出瓶颈，并给出优化方案。
