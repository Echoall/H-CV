# P4 图传与上位机

**阶段目标**：满足题目要求 1（M10），并且保证**不拖累测量**。

**本阶段需要的实物**：

- 一台将来要封存的接收笔记本（或平板）。在它到位之前，可以先用任意一台 Windows 笔记本开发。
- 一部手机：运行毫秒级秒表，用来测图传延迟。
- 一部用来拍照的设备。
- （备用）一台便携路由器。

**质疑要求**：

- 推流和测量之间有没有隐性的相互影响？例如内存带宽占用、编码器卡住时会不会连带阻塞主循环。
- 录像真的完整吗？要用 `ffprobe` 检查，不能只看文件大小。

## P4-T01 RTSP 推流（硬件路径）

**目标**：按 05 §2 实现推流。

**要求**：

1. 优先把 CHN1 直接绑定到 H.264 编码器，再接 RTSP。如果绑定方式不可行，就用传物理地址的方式送码流（`rtspserver_sendvideodata_byphyaddr`）。**不要**用 Python 逐包复制码流。实现方式和理由写进报告。
2. 分辨率、帧率、码率、GOP 都可以在 `config.json` 中配置。要确认 sensor 帧率（例如 90fps）和推流帧率（例如 30fps）之间的抽帧在哪一层完成。
3. 实现 AP 模式：SSID 和密码从 `config.local.json` 读取，可以指定信道。同时保留 STA 模式作为备选。
4. 推流异常必须和测量隔离：客户端断开、重连，或者 WiFi 掉线，都不能让测量主循环停顿超过 1 帧（附证据：断开和重连前后的帧间隔统计）。
5. 在 STATUS 和遥测中如实上报推流状态。

**验收标准**：

- [ ] VLC（`--network-caching=200`）和 ffplay 都能拉到流，附截图和命令。
- [ ] 客户端反复断开、重连 20 次后，测量的帧间隔 p99 不变（附数据）。

## P4-T02 UDP 遥测

**目标**：按 ICD §4.3 实现遥测。

**要求**：HELLO 登记；T、S、E 三种行；按 100ms 打包成数据报发送；5s 没有收到 HELLO 就停止发送；不处理任何其他网络输入（合规要求）。

**验收标准**：

- [ ] 全帧率遥测时（每 100ms 一个包），测量帧率下降不超过 3%（对比开启和关闭遥测时的数据）。
- [ ] 电脑端收到的 T 行 seq 连续率 ≥ 99%。
- [ ] 给 K230 的遥测端口发送垃圾数据，K230 不受影响（附测试）。

**要求**：

## P4-EXP12 图传性能与影响 🖐

**问题**（ADR-09）：

- 图传的延迟、稳定性和画质能否达标？
- 它对测量有多大影响？
- AP 模式好，还是路由器（STA）模式好？用哪个信道？

**方法**：按 06 T7 的 6 项测试执行，然后扩展：

1. **参数组合**：分辨率（1280×720 / 960×540）× 帧率（30 / 60）× 码率（1 / 2 / 4 Mbps），每种组合测：显示延迟、卡顿次数、对测量帧率和延迟的影响、画质（刻度能否看清）。
2. **网络**：AP 模式和便携路由器 STA 模式对比；信道 1、6、11 对比（周围用手机热点制造干扰）。
3. **距离**：2m、4m、6m，中间有人走动遮挡。
4. **时间对齐偏差**：拍摄 LED 闪烁，测出视频通道和遥测通道之间的固定偏差。
5. **K230 端叠加（可选）**：试验 OSD 或 WBC 叠加文字，测它对测量的影响。

**产出**：推荐的参数组合和网络模式，以及给出结论：ADR-09 是否成立。如果不成立，按推翻条件启动备用方案（05 §4），并提交 CR。

**验收标准**：

- [ ] M10 的各项都有数据。
- [ ] 推荐配置下，测量帧率下降 ≤ 10%，延迟增加 ≤ 5ms。

## P4-EXP13 TF 卡本地备份录像（可选）

**问题**：能否在 K230 上同时用 `mp4muxer` 往 TF 卡写一份备份录像？

**方法**：

1. 开启本地录像，同时运行完整管线，连续 10 分钟，测量它对测量帧率和延迟的影响。
2. 模拟录像过程中突然断电（拔掉电源），共 5 次。重新上电后检查文件能否打开，以及能恢复多少内容。

**验收标准**：

- [ ] 给出是否启用的建议。启用的前提是：对测量的影响 ≤ 3%，并且断电后至少能保留断电前 10s 以外的全部内容。
