# P0 基线：板卡接入与摄像头摸底

**阶段目标**：让 Codex 能可靠、可复现地操控 K230，并用实测数据回答"这个板子和摄像头到底能做到什么"。后面所有设计都建立在这些数据之上。

**本阶段需要的实物**：K230 板（含 GC2093 摄像头、TF 卡）、USB 数据线、1 根杜邦线（串口回环用）、万用表、尺子（≥ 30cm）或打印的网格纸、卷尺。

**质疑要求**：本阶段的核心任务是**检验 `docs/reference/K230硬件资料.md` 和 ADR-05、07、09 的前提假设**。如果发现任何与文档不符的地方，都必须记下来；影响方案的，要提交 CR。

---

## P0-T02 板卡访问工具

**目标**：把"上传文件、运行脚本、取回结果"变成可复现的命令。

**步骤**：

1. 选定访问方式（USB raw REPL、CanMV 的 VS Code 扩展命令行，或者其他方式），把选择理由写进 `docs/dev-setup.md`。可以参考调研中其他队伍的做法（树莓派队的 `k230_tool.py`，用 raw REPL 运行，长时间任务加 `--stream`）。
2. 在 `tools/board/` 中实现以下子命令：
   - `board.py info`
   - `board.py put <本地> <板上>`
   - `board.py get <板上> <本地>`
   - `board.py ls <目录>`
   - `board.py run <本地脚本> [--timeout s] [--stream] [--log 文件]`
   - `board.py reset`
3. `run` 要能实时收集板上的 `print` 输出，存成日志；超时后能中断板上程序，并让板子回到可用状态。
4. 首次连接时，备份 TF 卡上的文件清单和原有 `main.py`（AGENTS §5）。

**验收标准**：

- [ ] 连续 20 次「上传 → 运行一个打印 1000 行的脚本 → 取回结果」，**20 次全部成功**，输出没有丢行（附日志）。
- [ ] 板上脚本进入死循环时，`run --timeout 5` 能把它停下来，并且之后还能继续使用板子（附日志）。
  - **v1.2 修订（2026-11-20，依据实测 `e1b72b6` 及之后的复测）**：把这一条拆成两项，分别判定。**(i) 板端自退出**：脚本按 AGENTS §7 的自保护约定写，到达截止时间后自行退出，随后执行 `info` 成功，不需要断电。**这一项计入验收。****(ii) 电脑端用 Ctrl-C 中断**：实测 FAIL，作为已知限制记录在报告里，不计入验收。以后如果有空闲时间，可以低优先级再研究一下：friendly REPL 模式下按 Ctrl-C 有没有效，以及 CanMV IDE 的停止机制是怎么实现的。
  - **v1.3 补充（2026-11-20）**：根因已经找到，是 Ctrl-C 必须以单字节发送（AGENTS §7）。改正后，(a) 和 (b) 两种情况由电脑端中断都已 PASS。(c) 纯 `pass` 循环只在队员在场时复测一次，结果仅作记录，不计入验收。
- [ ] 原有 `/sdcard` 文件清单和 `main.py` 的备份已经提交。

## P0-EXP00 板卡基线盘点

**问题**：我们手上这块板子的固件、模块和 API，和文档写的一样吗？

**步骤**：用一个脚本自动收集以下信息，原样保存为 JSON：

1. 固件版本和编译时间（`os.uname()`、`sys.implementation` 等），CanMV 版本，固件文件名（问队员，或者从 TF 卡上读取）。
2. 内存：`gc.mem_free()`。如果 `media` 模块提供媒体内存或 MMZ 信息，也一并记录。
3. 可以导入的模块清单，至少检查：`media.sensor`、`media.media`、`media.display`、`media.vencoder`、`multimedia`、`ulab`、`image`、`cv2`、`cv_lite`、`nncase_runtime`、`network`、`socket`、`_thread`、`machine`（及其中的 `WDT`、`UART`、`FPIOA`、`Pin`）。
4. 各个对象的 API 列表：`dir(Sensor)`、`dir(Sensor 实例)`、`dir(image.Image)`、`dir(UART)`；`multimedia` 和 RTSP 相关类的方法；Encoder 的方法；`network.WLAN` 的方法。
5. Sensor 自动识别出来的型号，以及它支持的模式列表（如果有接口可以列出）。
6. `ulab` 的版本，`ulab.numpy` 中有哪些函数（特别是 `mean(axis)`、`argmax`、`cumsum`/`diff`、`convolve`、`median`、`sort`）。
7. `Image` 对象有没有 `to_numpy_ref`，以及 `find_blobs`、`get_statistics`、`get_histogram` 能不能用。

**产出**：`reports/P0-EXP00-板卡基线.md`，附原始 JSON。报告中要有一节「与文档不符之处」。

**验收标准**：

- [ ] 上面 1–7 项都有原始输出。
- [ ] 明确回答以下问题：有没有 `cv2` 或 `cv_lite`？`to_numpy_ref` 能不能用？有没有 `machine.WDT`？RTSP 和编码器有哪些可用接口（列出方法名）？

## P0-T03 串口回环与电平确认 🖐

**目标**：确认用于连接 MCU 的串口能正常收发。**v1.1**：板子是幻尔 K230，暂定使用 UART1（IO3 为 TX，IO4 为 RX）。**这项任务暂停，等拿到幻尔 40-pin 排针定义、确认物理脚位和电平后再做。**

**步骤**：

1. 🖐 队员用万用表测量：板子上电并运行一个配置好 UART2 的脚本后，TX 所在排针脚（以幻尔引脚图为准）对 GND 的空闲电压。应约为 3.3V；如果接近 0V，就先检查 FPIOA 配置（调研中有队伍遇到过）。
2. 🖐 队员用一根杜邦线短接 TX 和 RX（第 2、3 脚）。**不要接 V 脚。**
3. 回环测试：在 115200、460800、921600 三种波特率下，各发送 10,000 帧随机长度、随机内容的数据，比对收到的数据。
4. 用 FPIOA 正确配置引脚的示例代码要整理成 `k230/hcv/link_uart.py` 的雏形。

**验收标准**：

- [ ] TX 空闲电压实测值（附照片或读数）在 3.0–3.5V 之间。
- [ ] 三种波特率下，误码数都是 0（附日志和统计脚本）。

## P0-EXP01 摄像头模式、帧率、多通道、硬件裁剪

**问题**（影响 ADR-05、ADR-09）：

- Q1：GC2093 的 1280×720@90、1280×960@60、1920×1080@60、1920×1080@30 这几个模式，实际帧率和帧间隔抖动是多少？
- Q2：检测通道（CHN0）能不能输出 GRAYSCALE？在 640×360、640×480、320×180 等尺寸下，snapshot 的耗时分别是多少？
- Q3：同时开启 CHN1（YUV420SP 1280×720，只开启不取帧；或者绑定到编码器，P4 再细测）时，CHN0 的帧率会不会下降？
- Q4：`set_framesize(..., crop=(x,y,w,h))` 这类**通道级硬件裁剪**能不能用？裁剪后帧率是否提高、snapshot 是否更快？能不能只裁剪 CHN0，而 CHN1 保持全画面？
- Q5：一帧画面从拍摄到 snapshot 能拿到，大约要多久？（粗测即可，P3 用 LED 法精测。）

**方法**：

- 每种组合连续取 1,000 帧，记录每帧 snapshot 返回时的 `ticks_us`，以及 snapshot 调用本身的耗时。
- 组合包括：4 种 sensor 模式 × CHN0 的 3 种尺寸 × CHN1 开或关 × 裁剪开或关。不支持的组合要记录下来，并写明原因（报错信息原文）。
- 注意（**CR-P0-01 已批准**）：初始化顺序以**本板固件版本对应的官方例程**为准。CanMV v1.4-a7de1c8 的顺序是：配置 Sensor → `MediaManager.init()` → `sensor.run()` → 采集 → `sensor.stop()` → `MediaManager.deinit()`。不同组合之间要完整释放资源再重新初始化；如果需要重启板子，要在报告中说明。

**产出**：报告中给出每种组合的平均帧率、p50/p95/p99/最大帧间隔、snapshot 耗时分布、错误信息。最后给出**推荐的 sensor 模式和检测通道配置**，并写明理由。

**验收标准**：

- [ ] Q1–Q4 都有数据支持的回答；Q5 有粗测值。
- [ ] 推荐配置下，CHN1 开启时 CHN0 的平均帧率 ≥ 60Hz，并且 p99 帧间隔 ≤ 2 倍标称值；做不到就如实写 FAIL，并提交 CR。

## P0-EXP02 ISP 控制能力 🖐

**问题**（影响 ADR-07）：能不能关闭或锁定自动曝光、自动增益和自动白平衡？能不能手动设置曝光时间？

**步骤**：

1. 根据 P0-EXP00 列出的 API，以及固件自带的 examples 和源码文档，找出所有和曝光、增益、白平衡、ISP 相关的接口。如果 Python 层没有提供，也要查一下有没有 ISP 配置文件或底层接口可以调用。
2. 🖐 光照阶跃测试：摄像头对着一张白纸，队员按提示开、关台灯（每个状态保持 3s，重复 5 次）。记录 ROI 的平均亮度随时间的变化：
   - (a) 默认自动模式；
   - (b) 锁定或手动曝光（如果能做到）。
3. 如果可以手动设置曝光：测试 1ms、2ms、4ms、8ms 曝光下的亮度和噪声（对着静止的白纸，计算像素的时间标准差）。

**产出**：报告给出接口清单，以及每个接口的效果（附亮度时间曲线）。

**验收标准**：

- [ ] 明确回答"能 / 不能锁定曝光"，并附证据。能锁定的话，给出推荐用法的代码。
- [ ] 给出自动曝光在光照阶跃后的稳定时间（ms），这关系到人从摄像头前走过时画面的亮度波动。

## P0-EXP03 视场角与畸变 → 安装高度 🖐

**问题**（影响 ADR-03，输出给结构组）：GC2093 镜头的视场角和畸变各有多大？摄像头要装多高？

**步骤**：

1. Codex 生成一张可打印的网格图（PDF 或 PNG：A4 纸，10mm 一格，中心有十字，标好尺寸），提交到 `tools/print/`。
2. 🖐 队员把网格纸平铺在桌面上，让摄像头**镜头正对纸面向下**，分别放在镜头到纸面 200mm、250mm、300mm 三个高度。用卷尺量出高度（精确到 ±2mm），每个高度拍 3 张。使用推荐模式（EXP-01 的结论），保存全分辨率原图。
3. 分析：
   - 由网格计算水平和垂直视场角，以及每个像素对应的毫米数（画面中心和边缘分别算）。
   - 径向畸变：网格直线的弯曲程度，以及边缘处的尺寸缩放比例。
4. 计算安装高度：画面要覆盖 270mm 的有效宽度（摆杆 250mm 加上两侧余量），另外再留 10% 的安装余量。给出**最低高度 H_min**和**推荐高度**，以及推荐高度下检测通道的 mm/px。
5. 结合 02 §2 的倾斜误差模型，估算推荐高度下 θ = 6° 和 θ = 10° 时的未补偿误差。

**产出**：报告和一页「给结构组的安装建议」（`reports/P0-给结构组的安装建议.md`），内容包括：高度范围、光轴竖直度、画面方向、支架刚度要求（引用 07-B）。

**验收标准**：

- [ ] 视场角、畸变、mm/px 都有实测数据，三个高度的结果一致（视场角相差 ≤ 2°）。
- [ ] 给出 H_min、推荐 H，以及推算过程。
